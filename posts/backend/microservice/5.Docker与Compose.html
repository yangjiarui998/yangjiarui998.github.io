5. Docker 与 Docker Compose ​

5.1 它在项目里干什么 ​

Docker 是所有中间件 + 三个 .NET 服务的运行底座，Compose 负责把 7 个容器编成一个能一次起来的整体：统一网络（服务名互访）、统一的健康检查与启动顺序、统一的卷和环境变量。

  • 镜像构建：SDK 镜像编译 → aspnet 镜像运行（多阶段）。
  • 编排：compose.yaml + .env，一条 docker compose up -d --build。
  • 完整版本见 7. Deploy。

5.2 .NET 10 镜像 ​

项结论
采用mcr.microsoft.com/dotnet/sdk:10.0（构建）、mcr.microsoft.com/dotnet/aspnet:10.0（运行）
状态.NET 10 于 2025-11-11 GA，LTS，支持到 2028-11-14；这两个 tag 在 Microsoft 官方教程里逐字出现
基础系统.NET 10 默认镜像已从 Debian 换成 Ubuntu 24.04 "Noble"，不再提供 Debian 变体；10.0 与 10.0-noble 等价
默认端口.NET 8 起容器默认端口由 80 改为 8080（ASPNETCORE_HTTP_PORTS=8080），并以非 root 用户 APP_UID=1654 运行
注意10.0 是浮动 tag，每月补丁会变；生产要钉补丁版或 digest（docker buildx imagetools inspect）

来源：.NET 支持政策 · 官方 .NET 10 容器教程 · 默认镜像改 Ubuntu 的说明 · 支持 tag 政策

5.3 官方风格的 Dockerfile ​

src/Order.Api/Dockerfile（另外两个服务把项目名 / dll 名替换即可）：

dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

# 先只拷项目文件并 restore，改业务代码时这一层能命中缓存
COPY MicroShop.slnx ./
COPY src/Shared/Shared.csproj src/Shared/
COPY src/Order.Api/Order.Api.csproj src/Order.Api/
COPY src/Product.Api/Product.Api.csproj src/Product.Api/
COPY src/Ocelot.Gateway/Ocelot.Gateway.csproj src/Ocelot.Gateway/
RUN dotnet restore src/Order.Api/Order.Api.csproj

COPY . .
RUN dotnet publish src/Order.Api/Order.Api.csproj -c Release -o /app/publish --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /app/publish ./
EXPOSE 8080
ENTRYPOINT ["dotnet", "Order.Api.dll"]

对照 Microsoft Learn 官方示例，四处要点：

  1. COPY *.csproj + RUN dotnet restore 单独成层，官方原话是让 csproj 「copied and restored as distinct layers」。
  2. dotnet publish -c Release -o /app/publish --no-restore；-c Release 对 net8.0+ 已是默认值，写上也无妨。
  3. EXPOSE 8080 只是元数据，真正发布端口靠 Compose 的 ports；不写也能跑。
  4. 官方还有一条无 Dockerfile 的路线：dotnet publish /t:PublishContainer，适合 CI 里统一产出镜像。

5.4 Compose 规范要点 ​

yaml
services:
  order-api:
    build:
      context: .
      dockerfile: src/Order.Api/Dockerfile
    environment:
      SERVICE_HOST: order-api
      SERVICE_PORT: "8080"
      DB: "Host=postgres-order;Port=5432;Database=orderdb;Username=postgres;Password=${POSTGRES_PASSWORD}"
    depends_on:
      postgres-order:
        condition: service_healthy
      rabbitmq:
        condition: service_healthy
      consul:
        condition: service_healthy
    restart: unless-stopped

规则说明
不写 version:顶层 version 已被官方标记 obsolete，用了会告警；Compose 一律用最新 schema 校验
condition: service_healthy依赖服务必须自己定义了 healthcheck 并变成 healthy，门控才会放行；service_started 只保证容器已启动、不等待就绪
healthchecktest 首项须是 NONE/CMD/CMD-SHELL；interval/timeout/start_period 是 duration，retries 是整数
.env 与 ${VAR}非密配置与密码走 .env，compose 会插值；${VAR:?报错} 可强制必填。密钥更高一级用顶层 secrets（官方镜像支持 *_PASSWORD_FILE）
服务名即 DNS同一个 Compose 默认网络里，容器之间用服务名互访；容器内 localhost 指自己，不能用来连别的容器
局限depends_on 只管单主机启动顺序，不能替代应用自身的连接重试；docker compose run 也不等健康条件

常用命令：

bash
docker compose config                  # 解析、插值、校验（只校验用 -q）
docker compose up -d --build           # 构建镜像并后台启动
docker compose up -d --wait            # 等到所有 healthcheck 通过再返回（需定义 healthcheck）
docker compose ps                      # 看状态与端口
docker compose logs -f order-api       # 跟日志
docker compose exec consul consul members
docker compose down                    # 停，保留卷
docker compose down -v                 # 停并删卷 —— 数据库会被清空，别手滑

5.5 管理控制台（Console）使用 ​

Docker 本身没有必须打开的 Web 控制台，按熟悉程度选一个：

  • Docker Desktop Dashboard（本机最直观）：Containers 列表看每个容器的状态/端口，点进去有 Logs / Inspect / Bind mounts / Stats，还能一键开终端。本机开发首选。
  • 命令行（服务器/远程机）：docker compose ps、docker compose logs -f <服务>、docker stats，以及 docker inspect <容器> 看返回 JSON 里 State.Health 的健康检查输出。
  • Portainer（第三方 Web 面板）：适合给不熟命令的同事看容器与卷；属于独立项目，本目录不给未经核验的安装清单。

排障时这三处最有用：docker compose ps 的 STATUS、logs 里的连接异常、inspect ... State.Health 里的健康检查输出。

5.6 排错 ​

现象原因 / 改法
服务一直 starting / 依赖卡住depends_on: service_healthy 但被依赖方没写 healthcheck；补上或改 service_started
应用容器反复重启十有八九地址还写 localhost；容器里要用服务名。看 docker compose logs -f order-api
docker compose config 报变量为空.env 没放对目录，或没用 ${VAR:?} 兜底；docker compose config 会打印插值结果
构建很慢.dockerignore 没排除 bin/obj；把 csproj 与 restore 拆成独立层
运行时报 Order.Api.dll 找不到多阶段 Dockerfile 漏了 COPY --from=build /app/publish ./ 或 WORKDIR /app
改了代码但容器里还是旧的没 --build；或层缓存命中旧 COPY，确认 .dockerignore 与上下文
down -v 后数据全没了具名卷被删，符合预期；想保留数据只 down
镜像 tag 是 latest 无法回滚用固定版本 tag / digest，见 6.Jenkins 的回滚章节

5.8 上生产的差距 ​

  • 镜像钉补丁/digest，推到私有 registry，不用 latest；CI 里生成 SBOM、扫漏洞。
  • 用 secrets 管理密码，别把 .env 提交进仓库；构建上下文排除 .env。
  • 加 deploy.resources.limits（CPU/内存）与 logging 的 max-size/max-file，避免日志撑爆磁盘。
  • 容器以非 root 运行（.NET 10 aspnet 镜像默认已是），只读根文件系统能开就开。
  • 集中日志与指标；健康检查要覆盖业务就绪而不只是进程存活。
  • Compose 适合单机/开发环境；多主机、滚动升级、自愈要考虑 Swarm / Kubernetes / 托管容器服务。
