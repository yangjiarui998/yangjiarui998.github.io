6. Jenkins 持续集成与发布 ​

6.1 它在项目里干什么 ​

把 7. Deploy 的手动步骤固化成流水线：dotnet build → 校验编排 → 构建镜像 → 起全套 → 冒烟检查。CI 是可选件，本地开发不需要它。

原教程的 Jenkinsfile 有三处硬伤，本篇已修掉：

原写法问题
agent any + shsh 是 Unix 步骤，Windows agent 上要用 bat / powershell；官方 jenkins/jenkins:lts 也不含 .NET SDK 与 Docker CLI
回滚段 docker tag ... --build-arg ...docker image tag 只有 SOURCE TARGET 两个位置参数，没有 --build-arg；那是 docker build 的参数。这是一条无效命令
up -d 后立刻 curl容器还没就绪就会失败；要 --wait 或带重试

6.2 版本与前置 ​

项结论
镜像jenkins/jenkins:lts-jdk21（官方当前推荐 LTS tag；latest 指向 weekly，不是 LTS）
镜像里没有Docker CLI、Compose V2 插件、.NET SDK。官方安装文档原话是 "this image doesn't contain Docker CLI"
因此「装好 .NET SDK 和 Docker 就行」不成立还需要 Compose V2 插件、Docker daemon 访问权限、curl、git，Windows 还要换步骤类型

来源：Jenkins 官方 Docker 安装文档 · Pipeline sh 步骤 · Compose 插件安装

6.3 三种真实可用的接法（先选一种） ​

方案怎么做优点代价 / 风险
A. 宿主机 agent（推荐）Jenkins 装在一台 Linux 机器上，agent 预装 .NET 10 SDK、Docker Engine、docker-compose-plugin、curl、git；jenkins 用户加入 docker 组最少改动，Jenkinsfile 直接能跑，最好排查docker 组等同 root 级权限，只给可信 job 用
B. 自定义 controller 镜像 + docker.sock基于 jenkins/jenkins:lts-jdk21 自建镜像，按 Docker 官方 apt 源说明 装 docker-ce-cli + docker-compose-plugin，并挂 /var/run/docker.sock全容器化，CI 环境可复制挂载 docker.sock 让容器能无限制改宿主机文件系统，官方安全文档明确警告；自建镜像要自己维护
C. Docker agent 跑构建，宿主机做部署agent { docker { image 'mcr.microsoft.com/dotnet/sdk:10.0' } } 跑 dotnet build/test，镜像构建与部署仍交给能访问 daemon 的节点构建环境干净、版本钉死需设 DOTNET_CLI_HOME=/tmp/dotnet 等权限，多一层调度；部署节点仍要有 Docker 权限

挂载 /var/run/docker.sock 的风险不是危言耸听：Docker 官方写的是「docker 组授予 root 级权限」「容器访问 daemon API 很容易导致权限提升」。生产可考虑 Rootless Docker，或官方 docker:dind + TLS（DOCKER_HOST=tcp://docker:2376、DOCKER_TLS_VERIFY=1）方案。

下面按方案 A 给可直接用的配置。

6.4 Jenkinsfile（Linux agent） ​

groovy
pipeline {
    agent any

    stages {
        stage('Checkout') {
            steps { checkout scm }
        }
        stage('Build') {
            steps { sh 'dotnet build -c Release' }
        }
        stage('Validate Compose') {
            steps { sh 'docker compose config -q' }
        }
        stage('Images') {
            steps { sh 'docker compose build' }
        }
        stage('Deploy') {
            steps { sh 'docker compose up -d --wait' }
        }
        stage('Smoke') {
            steps {
                sh 'curl --retry 10 --retry-delay 3 --retry-connrefused -fsS http://localhost:8080/orders'
            }
        }
    }
    post {
        always { sh 'docker compose ps' }
    }
}

要点：

  • docker compose config -q 先把 .env 缺失、YAML 错误挡在构建阶段，不会误部署。
  • up -d --wait 等到 healthcheck 通过再返回（需要 compose 里定义了 healthcheck，见 5.Docker与Compose）。
  • 冒烟用 curl --retry ... --retry-connrefused，不再假设 up -d 后服务立刻可用。
  • Windows agent：把 sh 换成 bat / powershell，或用 isUnix() 分支；checkout scm 两边通用。
  • 失败时流水线停在失败的 stage，post.always 仍会打印 docker compose ps，方便看是哪个容器没起来。

6.7 排错 ​

现象原因 / 改法
dotnet: not foundagent 没装 .NET 10 SDK；或用了官方 Jenkins 镜像当执行节点
docker: not found / docker: 'compose' is not a docker command缺 Docker CLI 或 Compose V2 插件；按官方说明装 docker-compose-plugin，用 docker compose（不是 docker-compose）
permission denied ... docker.sockagent 用户没进 docker 组；或 socket 没挂进容器
Windows agent 报 sh 不识别用 bat / powershell 或 isUnix() 分支
部署阶段卡住不返回--wait 依赖 healthcheck；检查某个服务是不是一直没 healthy，docker compose ps 看
冒烟 000 / connection refused服务还没就绪；已经有重试仍失败就看 docker compose logs -f ocelot-gateway
构建成功但部署的还是旧代码up -d --wait 前没有 build，或镜像 tag 用了 latest 且缓存命中

案例为什么可信

6.9 上生产的差距 ​

  • 凭据（registry、.env、SSH）进 Jenkins Credentials，不要写进 Jenkinsfile。
  • 不要把 docker.sock 暴露给不可信流水线；用独立部署节点、Rootless 或 dind + TLS。
  • 镜像 tag 用构建号 / commit SHA，禁用 latest；保留 N 个可回滚版本并演练回滚。
  • 加测试阶段与人工确认（生产部署），冒烟检查覆盖下单链路而不只是 /orders。
  • 构建产物与日志留存、失败告警；controller 的 JENKINS_HOME 定期备份。
