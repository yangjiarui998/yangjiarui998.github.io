3. PostgreSQL 双库与 Outbox 存储 ​

3.1 它在项目里干什么 ​

两个服务各有一份独立的库（微服务「一服务一库」的最小体现）：

容器库宿主端口里面有什么
postgres-orderorderdb5432Orders 业务表 + cap.published / cap.received 消息表
postgres-productproductdb5433Products、ProcessedEvents + CAP 消息表

CAP 的 Outbox 就落在业务库里：下单时「写订单」和「写待发消息」在同一个本地事务完成，消息再异步投递到 RabbitMQ，这是这套微服务保证最终一致性的关键。

3.2 版本与 PGDATA 的坑 ​

项结论
采用镜像postgres:16.15-alpine（把浮动 tag 钉死到补丁版）
16 是否过时否。PostgreSQL 16 支持到 2028-11-09；当前最新是 18，但没必要为了追新改挂载
为什么钉补丁16-alpine 会随小版本浮动，今天拉到 16.15、下个月可能是 16.16，不可复现
挂载路径PG17 及以下必须是 /var/lib/postgresql/data；PG18+ 改成了 /var/lib/postgresql（PGDATA=/var/lib/postgresql/18/docker），沿用旧路径会报错或数据悄悄落进匿名卷
结论保持 16 + 旧路径；将来升 18 必须同时改挂载并走 pg_dump/pg_upgrade

来源：官方版本策略 · Docker Hub PGDATA 章节 · docker-library/postgres PR #1259 · 18 的 Dockerfile

postgres.yaml（含可选的 pgAdmin 控制台，三者在同一默认网络里）：

yaml
services:
  postgres-order:
    image: postgres:16.15-alpine
    container_name: postgres-order
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: orderdb
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - pg-order:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d orderdb -h 127.0.0.1"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    restart: unless-stopped

  postgres-product:
    image: postgres:16.15-alpine
    container_name: postgres-product
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: productdb
    ports:
      - "127.0.0.1:5433:5432"          # 宿主 5433 → 容器 5432
    volumes:
      - pg-product:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d productdb -h 127.0.0.1"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    restart: unless-stopped

  pgadmin:                              # 可选：Web 控制台
    image: dpage/pgadmin4
    container_name: pgadmin
    environment:
      PGADMIN_DEFAULT_EMAIL: ${PGADMIN_EMAIL}
      PGADMIN_DEFAULT_PASSWORD: ${PGADMIN_PASSWORD}
    ports:
      - "127.0.0.1:5050:80"
    volumes:
      - pgadmin-data:/var/lib/pgadmin
    depends_on:
      postgres-order:
        condition: service_healthy
    restart: unless-stopped

volumes:
  pg-order:
  pg-product:
  pgadmin-data:

三个要点：

  • 端口：5433:5432 的右边永远是容器内的 5432；应用容器之间互连用 Host=postgres-product;Port=5432，写 5433 会连不上。
  • POSTGRES_* 只在数据目录为空时生效：已有卷时改 .env 不会改密码，要 ALTER USER postgres WITH PASSWORD '...'，或删卷重建。
  • 健康检查：pg_isready 不校验用户名/库名是否真实（写错也返回 0），加 -h 127.0.0.1 可以避免初始化阶段的 Unix socket 临时服务器造成误判；配合 start_period 和 depends_on: service_healthy。应用侧仍需自己重试连接。

3.4 管理控制台（Console）使用 ​

PostgreSQL 核心发行版没有自带 Web 控制台，只有命令行 psql；Web 界面要用独立项目 pgAdmin 4 / Adminer。

psql（最可靠） ​

bash
docker exec -it postgres-product psql -U postgres -d productdb

pgAdmin 4 ​

浏览器打开 http://localhost:5050，用 .env 里的邮箱密码登录 → 右键 Servers → Register → Server：

  • General → Name 随意；
  • Connection → Host name/address 填 postgres-order（Compose 服务名，不是 localhost，因为 pgAdmin 也是容器）；
  • Port 5432，Username postgres，Password 取 POSTGRES_PASSWORD。

dpage/pgadmin4 是 pgAdmin 官方容器，默认监听 80，PGADMIN_DEFAULT_EMAIL/PASSWORD 两个环境变量必填，数据卷 /var/lib/pgadmin。示例里省略了版本号（等于 latest），生产请钉一个确切版本。更轻量的备选是官方 compose 示例里用的 adminer。

3.5 建表：EnsureCreated 只是演示 ​

代码演示里用 Database.EnsureCreated() 建表并插入种子数据，这是为了不让读者先学迁移。EF Core 官方明确把它定位成「数据可以丢的原型 / 测试 / 本地缓存」的轻量方案：

  • 不生成 __EFMigrationsHistory，没有迁移历史；
  • 模型改了不会应用变更，且与 Migrations 互斥；
  • 库里一旦存在任意表就整体跳过建表。

生产应该 dotnet ef migrations add InitialCreate → Migrate()（或 migration bundle / 审阅过的 SQL 脚本），种子数据用 HasData 或幂等初始化脚本。来源：EnsureCreated 官方文档 · Migrations 官方文档

CAP 的消息表不用你管：CAP 启动时执行 CREATE SCHEMA IF NOT EXISTS "cap" 与 CREATE TABLE IF NOT EXISTS "cap"."published" / "cap"."received"，幂等、自动创建，不要写进 DbContext 或迁移里。注意它与 EnsureCreated() 存在建表顺序上的潜在竞争（CAP 先建了表，EnsureCreated 可能跳过业务表）——生产改用 Migrations 就没这个问题。

3.6 备份与恢复 ​

bash
# 逻辑备份（custom 格式，单库）
docker exec -t postgres-order pg_dump -U postgres -d orderdb -F c -f /tmp/orderdb.dump
docker cp postgres-order:/tmp/orderdb.dump ./orderdb.dump

# 恢复
docker cp ./orderdb.dump postgres-order:/tmp/orderdb.dump
docker exec -i postgres-order pg_restore -U postgres -d orderdb --clean --if-exists /tmp/orderdb.dump

3.7 排错 ​

现象原因 / 改法
应用报 Connection refused容器里 Host=localhost 指自己；改成 postgres-order / postgres-product，端口 5432
password authentication failed.env 与代码连接串不一致；已有卷时改环境变量无效，用 ALTER USER
容器反复重启、日志报 PGDATA 相关把 18+ 的卷挂到了 /var/lib/postgresql/data；保持在 16 或改挂 /var/lib/postgresql
pg_isready 显示 healthy 但应用连不上它不校验账号/库；看 docker compose logs postgres-order 是否打印 ready for start up
cap.published 表不存在CAP 没启动成功或连错了库；看应用日志；表由 CAP 自动建，不要手工建
ProcessedEvents 查不到表名带双引号且大小写敏感：select * from "ProcessedEvents";
docker compose down -v 后库存回到 100正常，卷被删了；想保留数据就别加 -v
pgAdmin 连不上数据库Host 填了 localhost；应填 Compose 服务名，且两个容器在同一网络

3.9 上生产的差距 ​

  • 密码走 Docker secrets（POSTGRES_PASSWORD_FILE）或密钥管理，别写在 compose / 代码里。
  • 数据库端口只绑 127.0.0.1，或干脆不映射到宿主、只放内部网络（Mastodon 的 compose 就是这么做的）。
  • 用 Migrations 而不是 EnsureCreated()；给 shm_size 留足（官方示例 128mb+）。
  • 定期备份并演练恢复；跨大版本升级提前规划 pg_dump/pg_upgrade。
  • 连接池、慢查询日志、监控（pg_stat_statements）、时区统一。
