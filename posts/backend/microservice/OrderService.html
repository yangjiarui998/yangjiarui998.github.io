OrderService：用 Docker 跑通一条下单链路 ​

这篇做一个最小的下单流程：下单 → 订单服务写自己的库 → 发一条事件 → 产品服务扣库存。客户端只认网关一个入口，3 个 .NET 服务加 4 个中间件全部跑在容器里，最后一条 docker compose up -d --build 起全套。

步骤在前、解释在后：前 13 步照着敲就行，为什么这么写集中在最后第 14 节，做完再回头看。

开始之前 ​

需要装好：

  1. Docker Engine + Compose V2 插件（Docker Desktop 自带），docker compose version 能输出版本号就行。
  2. .NET 10 SDK 可装可不装，只用于第 7 步编译校验；镜像构建用的是 Dockerfile 里的 SDK 镜像，没装 SDK 就跳过第 7 步。
  3. curl。

端口都是宿主机上的，容器内部一律监听 8080、靠服务名互访：

东西地址
网关 Ocelothttp://localhost:8080
产品服务直连http://localhost:5201
Consul UIhttp://localhost:8500
RabbitMQ 管理台http://localhost:15672
订单库 / 产品库127.0.0.1:5432 / 127.0.0.1:5433

文中所有代码块按顺序照抄，攒出来的就是完整可跑的工程。代码已用本机 .NET 10 SDK 编译通过。

src/Order.Api/OrdersController.cs

csharp
using DotNetCore.CAP;
using Microsoft.AspNetCore.Mvc;
using Shared;

namespace Order.Api;

[ApiController]
[Route("orders")]
public class OrdersController : ControllerBase
{
    private readonly OrderDbContext _db;
    private readonly ICapPublisher _cap;
    private readonly IConfiguration _config;

    public OrdersController(OrderDbContext db, ICapPublisher cap, IConfiguration config)
    {
        _db = db;
        _cap = cap;
        _config = config;
    }

    [HttpGet]
    public IActionResult Index() =>
        Ok($"order.api:{Environment.MachineName}:{_config["SERVICE_PORT"]} {DateTime.Now:HH:mm:ss}");

    [HttpPost]
    public async Task<IActionResult> Create([FromBody] CreateOrderRequest req)
    {
        var order = new Order
        {
            Id = Guid.NewGuid(),
            ProductId = req.ProductId,
            Count = req.Count,
            CreatedAt = DateTime.UtcNow
        };

        // 订单行与 cap.published 里的消息在同一个本地事务提交：
        // 要么订单 + 消息都在，要么都不在，不会出现「订单写了但消息丢了」。
        using (var tx = _db.Database.BeginTransaction(_cap, autoCommit: true))
        {
            _db.Orders.Add(order);
            await _db.SaveChangesAsync();

            await _cap.PublishAsync("order.created", new OrderCreatedEvent
            {
                EventId = order.Id.ToString("N"),
                OrderId = order.Id,
                ProductId = req.ProductId,
                Count = req.Count
            });
        }

        return Ok(new { order.Id });
    }

    // 故意留的重放入口：用同一个 eventId 反复发，用来观察消费端幂等是否生效。
    [HttpPost("replay")]
    public async Task<IActionResult> Replay([FromQuery] string eventId)
    {
        await _cap.PublishAsync("order.created", new OrderCreatedEvent
        {
            EventId = eventId,
            OrderId = Guid.NewGuid(),
            ProductId = 1,
            Count = 1
        });
        return Ok(new { eventId });
    }
}

public record CreateOrderRequest(int ProductId, int Count);

src/Order.Api/Program.cs

csharp
using Consul;
using DotNetCore.CAP;
using Microsoft.EntityFrameworkCore;
using Order.Api;

var builder = WebApplication.CreateBuilder(args);

// 不设环境变量时是本机默认值；容器里由 compose.yaml 的 environment 覆盖。
var servicePort = int.Parse(builder.Configuration["SERVICE_PORT"] ?? "5101");
var serviceHost = builder.Configuration["SERVICE_HOST"] ?? "localhost";
var consulAddress = builder.Configuration["CONSUL"] ?? "http://localhost:8500";
var pg = builder.Configuration["DB"]
    ?? "Host=localhost;Port=5432;Database=orderdb;Username=postgres;Password=postgres";

builder.WebHost.UseUrls($"http://0.0.0.0:{servicePort}");
builder.Services.AddControllers();
builder.Services.AddDbContext<OrderDbContext>(o => o.UseNpgsql(pg));

builder.Services.AddCap(x =>
{
    x.UseEntityFramework<OrderDbContext>();
    x.UseRabbitMQ(o =>
    {
        o.HostName = builder.Configuration["MQ_HOST"] ?? "localhost";
        o.UserName = builder.Configuration["MQ_USER"] ?? "admin";
        o.Password = builder.Configuration["MQ_PASSWORD"] ?? "admin";
        o.VirtualHost = "/";
        o.Port = 5672;
    });
});

var app = builder.Build();

using (var scope = app.Services.CreateScope())
{
    scope.ServiceProvider.GetRequiredService<OrderDbContext>().Database.EnsureCreated();
}

// 存活检查只回一个 ok，故意不查库：数据库慢一下不该让整个实例被摘掉。
app.MapGet("/health", () => Results.Ok("ok"));
app.MapControllers();

var registration = new AgentServiceRegistration
{
    ID = $"order-service-{Environment.MachineName}-{servicePort}",
    Name = "order-service",
    Address = serviceHost,
    Port = servicePort,
    Check = new AgentServiceCheck
    {
        HTTP = $"http://{serviceHost}:{servicePort}/health",
        Interval = TimeSpan.FromSeconds(5),
        Timeout = TimeSpan.FromSeconds(3),
        // Consul 规定最小 1 分钟，写 30 秒不会按 30 秒生效。
        DeregisterCriticalServiceAfter = TimeSpan.FromMinutes(1)
    }
};

using var consul = new ConsulClient(c => c.Address = new Uri(consulAddress));
await consul.Agent.ServiceRegister(registration);
Console.WriteLine($"[order-api] 已注册 {registration.ID}");
Console.WriteLine($"[order-api] 心跳   {registration.Check.HTTP}");

app.Lifetime.ApplicationStopping.Register(() =>
    consul.Agent.ServiceDeregister(registration.ID).Wait());

await app.RunAsync();

src/Product.Api/ProductDbContext.cs

csharp
using Microsoft.EntityFrameworkCore;

namespace Product.Api;

public class ProductDbContext : DbContext
{
    public ProductDbContext(DbContextOptions<ProductDbContext> options) : base(options) { }

    public DbSet<ProductItem> Products => Set<ProductItem>();
    public DbSet<ProcessedEvent> ProcessedEvents => Set<ProcessedEvent>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // 唯一索引是幂等的最后一道防线：
        // 两个消费者并发处理同一事件时，后提交的那条会撞索引失败。
        modelBuilder.Entity<ProcessedEvent>()
            .HasIndex(x => x.EventId)
            .IsUnique();
    }
}

public class ProductItem
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public int Stock { get; set; }
}

public class ProcessedEvent
{
    public int Id { get; set; }
    public string EventId { get; set; } = "";
    public DateTime ConsumedAt { get; set; }
}

src/Product.Api/ProductsController.cs

csharp
using DotNetCore.CAP;
using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;
using Shared;

namespace Product.Api;

[ApiController]
[Route("products")]
public class ProductsController : ControllerBase
{
    private readonly ProductDbContext _db;
    private readonly ILogger<ProductsController> _log;

    public ProductsController(ProductDbContext db, ILogger<ProductsController> log)
    {
        _db = db;
        _log = log;
    }

    [HttpGet("{id:int}")]
    public async Task<IActionResult> Get(int id)
    {
        var product = await _db.Products.FindAsync(id);
        return product is null
            ? NotFound()
            : Ok(new
            {
                product.Id,
                product.Name,
                product.Stock,
                Time = DateTime.Now.ToString("HH:mm:ss.fff")
            });
    }

    // [NonAction] 避免这个方法被误注册成 HTTP 接口；
    // topic 必须与发布端一字不差，否则消息会进队列但没人消费。
    [NonAction]
    [CapSubscribe("order.created", Group = "product-api")]
    public async Task ReduceStock(OrderCreatedEvent e)
    {
        // CAP 是「至少一次投递」：网络抖动、消费超时、手动重放都会带来重复消息。
        // 先判重，命中就直接返回，库存不会被扣第二次。
        if (await _db.ProcessedEvents.AnyAsync(x => x.EventId == e.EventId))
        {
            _log.LogInformation("事件 {EventId} 已处理过，跳过", e.EventId);
            return;
        }

        // 「减库存」和「记下 EventId」必须在同一个事务，
        // 否则中间失败会留下「扣了库存却没记判重」的缺口。
        await using var tx = await _db.Database.BeginTransactionAsync();

        var product = await _db.Products.FindAsync(e.ProductId);
        if (product is null) throw new Exception($"产品 {e.ProductId} 不存在");
        if (product.Stock < e.Count) throw new Exception("库存不足");

        product.Stock -= e.Count;
        _db.ProcessedEvents.Add(new ProcessedEvent
        {
            EventId = e.EventId,
            ConsumedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();
        await tx.CommitAsync();

        // 容器日志里留一行可观察的结果，验证时不用连数据库也能看到扣减是否发生。
        _log.LogInformation(
            "事件 {EventId}：产品 {ProductId} 扣减 {Count}，剩余库存 {Stock}",
            e.EventId, e.ProductId, e.Count, product.Stock);
    }
}

csharp
using Ocelot.Cache.CacheManager;
using Ocelot.DependencyInjection;
using Ocelot.Discovery.Consul;
using Ocelot.Middleware;

var builder = WebApplication.CreateBuilder(args);

var gatewayPort = int.Parse(builder.Configuration["GATEWAY_PORT"] ?? "5000");
builder.WebHost.UseUrls($"http://0.0.0.0:{gatewayPort}");

// OCELOT_CONFIG 让同一份镜像在容器里换成 ocelot.docker.json，
// 本机不设就读 ocelot.json。
builder.Configuration.AddJsonFile(
    builder.Configuration["OCELOT_CONFIG"] ?? "ocelot.json",
    optional: false, reloadOnChange: true);

builder.Services
    .AddOcelot(builder.Configuration)
    .AddConsul()                                    // 服务名 → Consul 里的 passing 实例
    .AddCacheManager(x => x.WithDictionaryHandle()) // 进程内缓存，仅演示
    .AddQualityOfService();                         // 熔断/超时，Ocelot 25 主包内置

var app = builder.Build();

app.MapGet("/health", () => Results.Ok("ok"));
await app.UseOcelot();

app.Run();

14.1 心跳检测 ​

服务启动时向 Consul 注册，只是登记一个地址，Consul 自己不会发现进程死了。没有健康检查时：容器 OOM、进程崩溃，注册记录都还在，网关会继续把请求转给这个死地址，客户端拿到 502 或超时且不会自愈。

Program.cs 里那一段各自的作用：

代码作用
app.MapGet("/health", ...)给 Consul 一个可探测的靶子
AgentServiceCheck.HTTPConsul 主动来探，而不是等应用上报
Interval / Timeout = 5s / 3s定义「多久之内必须发现故障」，越密发现越快、也越容易误判
DeregisterCriticalServiceAfter = 1min容器被强杀、来不及反注册时的兜底
ApplicationStopping.Register(...)正常退出时立刻下线，不用等那一分钟

两个容易踩的坑：Consul 规定反注册时间最小 1 分钟，写 30 秒不会按 30 秒生效；/health 故意不查库，因为这是存活检查（liveness）不是就绪检查（readiness），数据库慢一下就把还能接单的实例摘掉，会把局部抖动放大成整体不可用。

注册完为什么还要往日志打一行：这一步没有任何界面反馈，ServiceRegister 成功也不代表心跳地址写对了（地址写错要等十几秒才在 UI 上变红）。把注册 ID 和心跳地址打到日志里，docker compose logs 一查就能核对。消费端那两行同理，验证幂等不用先连数据库查表。

另外三个决定：注册 ID 带机器名和端口，所以起第二个容器时是两条独立记录；绑定 0.0.0.0 而不是 localhost，否则 Consul 从别的容器来探活永远失败；主动反注册 + 超时兜底两条路都留，对应 docker compose down 和容器被强杀两种退出。

14.2 容器里为什么全写服务名 ​

compose.yaml 里所有地址都是 postgres-order、rabbitmq、consul、order-api 这样的服务名，不是 localhost。7 个服务挂在同一个 micro-shop 网络，Docker 内置 DNS 把服务名解析成容器 IP。写 localhost 指的是容器自己，应用会去连一个根本不存在的数据库。

几个容易混的地方：

  • SERVICE_HOST 是注册给 Consul 的地址，必须是不带 scheme 的服务名；Consul 要反过来按这个名字探 http://order-api:8080/health。
  • SERVICE_PORT 是容器内部端口 8080，不是宿主映射端口 5201。
  • environment 覆盖 Program.cs 里的默认值，所以同一份代码本机和容器都能用，不用改代码、也不用改 appsettings.json。
  • OCELOT_CONFIG 让同一份网关镜像在容器里改读 ocelot.docker.json；两份配置只差 BaseUrl 和 ServiceDiscoveryProvider.Host。

14.3 Outbox：发消息为什么要开数据库事务 ​

下单要做两件事：写订单行、发事件。如果先写库再单独发消息，中间进程崩溃就会留下「订单存在、没有人去扣库存」的烂数据，且没有自动恢复。

OrdersController 用 BeginTransaction(_cap, autoCommit: true)，让订单行和 cap.published 里的消息在同一个本地事务里提交；CAP 后台再补发到 RabbitMQ。即便 RabbitMQ 当时不可用，消息也还在库里。一次成功下单会同时看到三处变化：订单表多 1 行、cap.published 多 1 条 Succeeded、product-api.v1 队列 Ready 回到 0。

代价是最终一致：下单返回成功时，库存可能还没更新。业务上要求「扣不到库存就不能下单」的话，这套方案不适用，得换成同步预留库存或 Saga。

14.4 幂等：消费端为什么自己记 EventId ​

CAP 和 RabbitMQ 保证的是至少一次投递：网络抖动、消费超时、手动重放都会带来重复消息，「恰好一次」只能业务侧自己兜。

防护做了两层：ProcessedEvent.EventId 上建唯一索引是一层；消费方法进来先判重、且「减库存」和「记下 EventId」放在同一个事务里是另一层。并发重复时，后提交的那条撞索引失败，CAP 重试后判重命中直接返回，库存仍只扣一次。

/orders/replay 是故意留的重放入口：用同一个 eventId 连打 3 次，改之前库存 100 → 97，加完判重是 100 → 99。没有这个入口，幂等是否正确只能靠等一次真实的网络重传。

14.5 网关：把地址和横切逻辑从业务里拿走 ​

客户端只认 :8080 一个入口，配置里写的是服务名，Ocelot 每次请求去 Consul 取 passing 实例再转发。应用代码里没有一行在做负载均衡、没有一行存着对方 IP。

开关加了看到什么代价
RoundRobin两个容器 ID 交替出现每次请求多一次服务发现查询
RateLimitOptions1 秒内第 6 次返回 429ClientIdHeader: "Host" 让所有客户端共用一个计数器，等于全局限流
CacheOptions5 秒内 Time 字段不变库存刚变更时读数可能旧 5 秒
QoSOptions下游挂掉时快速返回 503阈值太激进会把偶发抖动误判成故障

版本上有三个坑：Ocelot 25 缓存字段是 CacheOptions（FileCacheOptions 已废弃）；限流用 Period / Limit / StatusCode / QuotaMessage / EnableHeaders 这组新名字；默认按 Oc-Client 头识别客户端，识别不到会直接 503，示例改成 Host 只是为了让 curl 不加头也能演示。

14.6 关键决策与取舍 ​

决策为什么什么时候别这么干
事件驱动而非同步调用产品服务挂几分钟照样能收单，恢复后库存自动补齐要求「扣不到库存就不能下单」
Outbox 而非分布式事务一张本地消息表就换来「订单写了消息必在」，比引一套分布式事务框架轻得多跨多个服务要求严格原子性
业务侧自己做幂等中间件只承诺至少一次，「恰好一次」只能业务兜引入了事务性消费再重新评估
EnsureCreated() 而非 Migrations演示不必先学迁移，schema 变了删卷重来即可项目要长期维护，第一天就该换 Migrations
网关缓存放进程内而非 Redis少一个中间件网关起多实例，各缓存各的、数据打架
存活检查不查数据库数据库抖一下不至于把能接单的实例摘掉需要精确就绪判断时，另补 /ready 接编排探针
Compose 单机编排一条命令起全套，练手最省事要多机调度、自愈，上 K8s 或托管容器服务

14.7 这里没做的事 ​

认证鉴权、结构化日志与链路追踪、EF Core Migrations、/ready 就绪检查、判重表清理、CAP Dashboard 死信人工处理、TLS、重试退避、集成测试——都刻意没加，加了就看不见主线。要拿去上线，上面每一条都得补，最先补的是 Migrations 和 /ready。
