2. RabbitMQ 事件总线 ​

2.1 它在项目里干什么 ​

CAP 用 RabbitMQ 做跨服务事件传输：下单时订单服务在本地库写一条 Outbox 消息，CAP 把它投递到 RabbitMQ，产品服务订阅 order.created 后扣库存。RabbitMQ 挂了，消息会留在 cap.published 表里等重试，不会丢单。

它的 Web 控制台（Management UI）能看到 CAP 自动建的交换机、队列、消息速率，是排查「下单成功但库存没减」的第一站。

2.2 版本与变体 ​

项结论
采用镜像rabbitmq:4.4.0-management（2026-10 发布，官方下载页标注为最新）
原教程的 3.13-management-alpine3.13 社区支持 2024-09-30 结束；且 Alpine 变体的官方模板写着「Alpine Linux is not officially supported by the RabbitMQ team」
为什么不用 -alpine生产建议 Debian/Ubuntu 基底；-management 后缀仍受支持，自带 Management Plugin

健康检查为什么不是 ping：rabbitmq-diagnostics -q ping 是官方监控文档里的 Stage 1 检查，只验证 Erlang 运行时和 CLI 能认证，不保证 5672 已监听。check_port_connectivity 是 Stage 4，会对所有 listener 建 TCP 连接；配 start_period 给首次启动留出时间，应用侧再用 depends_on: condition: service_healthy 门控。官方镜像自身不带 HEALTHCHECK，必须自己写。

RABBITMQ_DEFAULT_* 只在空数据目录首次启动时生效：已有卷时改 .env 不会改密码，要么 rabbitmqctl change_password，要么删卷重建。这也是要固定 hostname 的原因——节点数据目录按 hostname 命名。

2.4 管理控制台（Console）使用 ​

浏览器打开 http://localhost:15672，用 .env 里的账号密码登录（该用户默认带 administrator tag）。

页面路径用途
Overview#/消息速率、节点内存/磁盘、连接总数
Connections / Channels#/connections / #/channels看 CAP 是否连上、有没有反复重连
Exchanges#/exchanges找 cap.default.router（topic、durable）
Queues#/queues找 product-api.v1，看 Ready / Unacked / 消费速率
Admin → Users / Vhosts / Policies / Limits#/users #/vhosts #/policies #/limits账号与权限管理

4.x 没有 #/admin 这个路由（Admin 只是导航分组，子项是 #/users 等），旧博客里写 #/admin 是错的。Queues 标签在 4.x 显示为 "Queues and Streams"。

常用操作：

  • 点进队列 → Get messages 看消息内容。注意 requeue=false 会把消息取走（等于消费），排错时选 requeue=true。
  • Purge / Delete 队列会在详情页；也可用 rabbitmqctl purge_queue <name>。
  • 排查失败消息请装 DotNetCore.CAP.Dashboard（x.UseDashboard()，路径 /cap）做人工重试，RabbitMQ UI 只能处理还留在队列里的消息。

2.5 guest / loopback 的真相（原教程最容易踩的坑） ​

这条结论分两层，网上大部分中文博客只写了其中一层：

  1. RabbitMQ 产品默认：guest 只允许从 localhost 连接，远程连接会被拒，日志是 PLAIN login refused: user 'guest' can only connect via localhost。放开要写 loopback_users = none，但官方标了 danger，强烈不建议。
  2. Docker 官方镜像例外：docker-library/rabbitmq 的 conf.d/10-defaults.conf 里就写着 loopback_users.guest = false，也就是官方镜像主动关闭了这个限制。所以用原版镜像时，另一个容器经 rabbitmq:5672 用 guest/guest 是能连上的。

那什么时候会真的报 ACCESS_REFUSED？——把宿主目录整体挂到 /etc/rabbitmq/ 会把镜像自带的 conf.d/10-defaults.conf 和 enabled_plugins 一起盖掉：guest 限制恢复、管理插件也不启动。修法是只挂单文件到 conf.d/，并改用自定义账号。

本目录直接用自定义账号，把这层隐式默认值彻底绕开。来源：访问控制 · 镜像默认配置源码 · 配置文档 · 可复现的故障实验

CAP 自动创建的拓扑（官方源码与文档核实）：

项值
交换机cap.default.router，类型 topic，durable（旧博客写的 cap.default.topic 已过时）
队列名Group + "." + Version → 本项目 [CapSubscribe("order.created", Group="product-api")] 得到 product-api.v1；不写 Group 才是 cap.queue.{程序集名}.v1
绑定消费者启动时按订阅 topic 作 routing key 自动 QueueBind
本地消息表cap.published / cap.received，位于 PostgreSQL 的 cap schema，由 CAP 启动时 CREATE TABLE IF NOT EXISTS 自动建，不需要 EF 迁移

上线顺序：CAP 只在消费者启动时声明队列和绑定；如果先发布、后起消费者，那批消息不会被该队列保留。整套部署要先起 product-api 再接受下单。UseEntityFramework<T>() 与 UsePostgreSql(conn) 二选一，不要同时调用。

官方 README 里出现过 x.DefaultGroup = ...，真实属性名是 DefaultGroupName，照抄会编译失败；本项目没有用到它，显式写 Group 即可。

来源：CAP RabbitMQ 文档 · 配置说明 · Dashboard · RabbitMQ 选项源码

2.7 排错 ​

现象原因 / 改法
应用日志 ACCESS_REFUSED账号密码与 .env 不一致；或整体挂载覆盖了 /etc/rabbitmq/；确认只挂单文件
ECONNREFUSED :5672健康检查用了 ping 提前放行；改 check_port_connectivity，应用侧重试
管理台打不开没用 -management 镜像；或整体挂载盖掉了 enabled_plugins；docker exec rabbitmq rabbitmq-plugins list
改了 .env 密码不生效RABBITMQ_DEFAULT_* 只在首次初始化生效；rabbitmqctl change_password 或删卷重建
容器重建后队列/用户全丢没挂 /var/lib/rabbitmq 具名卷，或 hostname 变了
下单成功但库存没减看 #/queues 里 product-api.v1 有没有消息；再查 cap.received；确认订阅的 topic 与 Group 一字不差
消息在队列里堆积消费者没起或抛异常；看应用日志，必要时用 CAP Dashboard 重试

2.9 上生产的差距 ​

  • 删除 guest、禁用 ANONYMOUS，每个应用一个账号 + 生成密码 + 细粒度权限，按 vhost 隔离，定期轮换凭据。
  • 启用 TLS（5671 / 15671），端口不要暴露公网。
  • 调 vm_memory_high_watermark.relative（0.4~0.7）、disk_free_limit.absolute（默认 50MB 只够开发）、文件句柄数。
  • 用 quorum 队列 / durable 队列；RabbitMQ 4.3 起默认禁用非持久化的非 exclusive 队列。
  • 拓扑用 definitions import 预先声明，别依赖「消费者启动才建队列」。
  • 监控：Prometheus 插件（15692）+ Grafana；日志聚合；NTP 时钟同步。
  • 参考官方 生产检查清单。
