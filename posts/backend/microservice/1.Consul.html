1. Consul 服务注册与发现 ​

1.1 它在项目里干什么 ​

Consul 是这套微服务的服务注册表 + 健康检查中心：

  • Order.Api / Product.Api 启动时用 Consul.NET 把自己的 地址:端口 注册进去，并挂一个 GET /health 检查；
  • Ocelot.Gateway 通过 AddConsul() 从 Consul 查 order-service / product-service 的可用实例，再按 RoundRobin 转发；
  • 实例挂了，健康检查变红，被自动从可用列表摘掉。

它同时带一个 Web 控制台（Consul UI），是本目录里最直观的一个 Console。

1.2 版本与许可（先看这个） ​

项结论
采用镜像hashicorp/consul:1.21.3（官方文档 compose 案例使用的确切 tag）
原教程的 1.20社区安全支持已于 2026-05-24 结束，不再使用
更新版本Docker Hub 2.0.4、GitHub 2.1.0；但 2.1.0 镜像把 iptables 换成 nftables，属破坏性变更，本地教程不追新
许可证1.17.0 起为 BUSL 1.1（Licensor: IBM），Change Date 为发布后 4 年、之后转 MPL 2.0；官方明确「组织内部自用不算竞争性提供」，本项目内部服务发现可免费用于生产
旧包名Docker Official Image consul 自 1.16 起停发，必须用 hashicorp/consul（Verified Publisher）

来源：Consul releases · EOL 日期 · LTS 政策 · BUSL 说明 · LICENSE 原文

1.3 单机部署（开发用） ​

新建 consul.yaml：

yaml
services:
  consul:
    image: hashicorp/consul:1.21.3
    container_name: consul
    command: "agent -server -bootstrap-expect=1 -ui -client=0.0.0.0"
    ports:
      - "127.0.0.1:8500:8500"       # HTTP API + UI
      - "127.0.0.1:8600:8600/tcp"   # DNS
      - "127.0.0.1:8600:8600/udp"
    volumes:
      - consul-data:/consul/data
    healthcheck:
      test: ["CMD-SHELL", "curl -fsS http://127.0.0.1:8500/v1/status/leader | grep -q ."]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 10s
    restart: unless-stopped

volumes:
  consul-data:

三个关键点：

  1. 没有写 -data-dir：官方镜像的 docker-entrypoint.sh 在第一个参数是 agent 时会自动追加 -data-dir=/consul/data -config-dir=/consul/config，镜像本身也声明了 VOLUME /consul/data。所以卷必须挂 /consul/data。
  2. 必须用具名卷：只靠镜像的匿名 VOLUME，容器重建后注册信息、KV 全丢。
  3. 健康检查用 /v1/status/leader：原教程的 consul members 只证明 gossip 成员在，不校验是否选出 leader、HTTP API 是否可用；grep -q . 是防止「无 leader 时返回空串但 HTTP 200」的误判。镜像的 Alpine 里装了 curl（Dockerfile 的 apk add ... curl ...）。

启动与验证：

bash
docker compose -f consul.yaml up -d
docker compose -f consul.yaml ps                       # STATUS 应为 healthy
curl -fsS http://localhost:8500/v1/status/leader       # 期望 "172.x.x.x:8300"
docker exec consul consul members                     # 期望 1 个 alive 的 server

1.4 管理控制台（Console）使用 ​

浏览器打开 http://localhost:8500/ui/（默认数据中心 dc1，-ui 已开启）。

页面路径能做什么
Services/ui/dc1/services看服务列表、实例数、健康检查绿勾/红叉；点服务进 /instances 看地址与端口
Nodes/ui/dc1/nodes看节点状态
Key/Value/ui/dc1/kv增删改查配置项
Access Controls/ui/dc1/aclsToken / Policy / Role（要先启用 ACL）

Services 页是只读的：不能在 UI 里点一下把僵尸实例注销掉（该按钮因 issue #2541 被移除）。反注册必须走 API 或 CLI：

bash
curl -X PUT http://localhost:8500/v1/agent/service/deregister/order-service-HOST-5101
docker exec consul consul services deregister -id=order-service-HOST-5101

bash

# 手动注册一个服务（PUT，注册到本地 agent，不是 catalog）

1.6 与 .NET 代码对接 ​

代码里的三个配置项（见 OrderService）：

配置本机 dotnet run容器里（compose）
CONSULhttp://localhost:8500http://consul:8500
SERVICE_HOST本机局域网 IP（不能填 127.0.0.1）order-api / product-api（compose 服务名，不带 http://）
SERVICE_PORT5101 / 52018080

健康检查的 URL 是 Consul 容器发起的，所以 SERVICE_HOST 必须能被 Consul 容器解析——这正是容器里要写服务名的原因；三个容器必须在同一个 Compose 网络里。Ocelot 的 ServiceDiscoveryProvider.Host 同理，容器里写 consul，不能写 localhost。

1.7 排错 ​

现象原因 / 改法
UI 里实例一直红 / critical健康检查 URL 写的 127.0.0.1 或 IP 已变；容器里改成服务名并确认同一网络
curl :8500/v1/status/leader 返回空还没选出 leader；docker compose logs consul 看 raft 报错；单节点要 -bootstrap-expect=1
容器一直 starting健康检查命令写错（比如镜像里没有 curl，或用了不支持的 shell）；docker inspect consul 看返回 JSON 里 State.Health 的最后一次输出
服务停了但 UI 里还在等满 DeregisterCriticalServiceAfter；正常 Ctrl+C 会主动注销，强杀进程才靠超时兜底
重启后注册信息没了没挂具名卷；或用了 -dev（内存模式）
应用报 Connection refused :8500CONSUL 还写着 localhost；确认 consul 容器 healthy
两个实例只剩一个注册 ID 必须带端口/机器名区分；同 ID 会相互覆盖

1.9 上生产的差距 ​

  • 单节点容错为 0：官方可靠性表明确建议生产 3 或 5 个 server，单 server 仅限开发。
  • 启用 ACL：注册/注销需 service:write，查询需 node:read,service:read；Ocelot 要配 Token，.NET 客户端也要带 Token。
  • 不要 -dev：它把持久化全关了，重启即丢。
  • 别只映射 8500：多节点集群还要 8300（server RPC）、8301/8302（Serf LAN/WAN，TCP+UDP）、8600（DNS，TCP+UDP），UDP 不能漏。
  • 端口别裸暴露：-client=0.0.0.0 是容器内部需要，宿主侧用 127.0.0.1:8500:8500 或只放内网。
  • 备份：定期 consul snapshot save 外置保存。
  • Compose 不是生产编排：HashiCorp 官方明确说 Docker Compose 适合开发探索，不建议用于生产部署。
