六、多线程与异步编程 ​

本篇把「C#.NET 拾遗补漏」系列中关于线程、Task 与 TAP 的三篇内容合并整理成一条知识线：先分清线程概念 → 再对比 Thread/ThreadPool/Task → 最后落到 async/await 与常用 TAP 操作。代码示例按现代 C# 语法精简重写。

6.1 线程、前台/后台线程、并行与并发怎么区分？ ​

**线程（Thread）**是操作系统能够进行运算调度的最小单位，是进程中的实际运作单位。严格来说，同一时刻真正能并行运行的线程数取决于 CPU 核数。

按运行模式分：

类型特点.NET 中的对应
前台线程主程序必须等它执行完才能退出new Thread(...) 默认是前台线程
后台线程主程序结束即随之退出，不管是否执行完ThreadPool 管理的线程默认都是后台线程
守护线程生命周期自动结束，常用于后台任务概念上与后台线程相近

成本提醒：每开一个线程都要消耗内存，即使什么都不做，栈也至少约 1MB。

**并行（Parallelism）与并发（Concurrency）**是高频面试题：

  • 并行：同一时刻多条指令在多个处理器上同时执行，宏观微观都同时；
  • 并发：同一时间段内宏观上"看起来同时"，微观上其实是多条指令快速切换，同一时刻可能只有一条在执行。

一句话记法：并行是真的同时，并发是轮流交替。

6.2 Thread、ThreadPool 和 Task 有什么区别？ ​

这是三者对比的结论表，也是回答"为什么现在都用 Task"的关键。

维度ThreadThreadPoolTask
本质操作系统级线程，有自己的栈和内核资源CLR 维护的一组线程的包装器TPL 提供的抽象，由 TaskScheduler 调度，默认跑在 ThreadPool 上
控制力最高：可 Abort/Suspend/Resume、设栈大小、Culture几乎无：只能控制池大小，无法知道任务何时开始中等：可 ContinueWith、等待、取结果
开销大：栈内存 + 上下文切换 CPU 开销小：复用已创建线程小，且不创建自己的 OS 线程
获取结果无直接机制，靠共享变量无完成通知、无返回值Task<T> 有 Result，可 await
适用场景明确需要独立线程执行长耗时任务不需要结果的短时操作绝大多数场景的默认选择

三个关键结论：

  1. Task 不是对线程的抽象，而是对"异步工作"的抽象。默认情况下 Task 在当前线程上执行，并酌情把工作委托给操作系统；只有显式 Task.Run 才会要求到线程池的另一个线程上跑。
  2. ThreadPool 无法检测任务何时完成，也没有获取结果的方法，因此只适合调用者不关心结果的短操作。往池里塞太多长任务会把它填满，后面的任务被迫排队。
  3. 所有较新的上层 API（Parallel.ForEach、PLINQ、async/await）都建立在 Task 之上。长耗时任务要用 TaskCreationOptions.LongRunning，它会让调度器另开线程而不是占用线程池。

实践准则：绝大多数情况用 Task，不要直接用 Thread，除非你明确需要一个独立线程跑长任务。

6.3 Task 与 Task<T> 是什么？ ​

Task 是 Promise（承诺）模型的 .NET 实现：它承诺"稍后完成工作"。

  • Task：不返回值的异步操作；
  • Task<T>：返回 T 类型结果的异步操作。

await 的价值在于：任务运行期间把控制权交还给调用者，让当前线程去做别的事，任务完成后恢复后续代码，不再需要回调或事件来串联流程。

6.4 I/O 受限 与 CPU 受限异步有什么不同？ ​

这是理解 async/await 收益的分水岭。

（1）I/O 受限：例如 HTTP 请求、文件读写。

public async Task<string> GetFirstCharsAsync(string url, int count)
{
    var client = new HttpClient();          // 同步执行
    var page = await client.GetStringAsync(url); // 交出控制权，线程去处理别的请求
    return count > page.Length ? page : page.Substring(0, count); // 恢复后同步执行
}

GetStringAsync 内部会层层调用到底层网络库 / 系统 API（如 Linux 的 write()），Task 对象沿调用链返回给初始调用者。整个等待过程中没有一个线程专门用来等这次 I/O——这是异步能大幅提升服务器吞吐量的根本原因。时间线可粗略理解为 0--1 是 await 之前的准备、1--2 是纯 I/O 等待（零 CPU 成本）、2--3 是恢复后继续执行。

（2）CPU 受限：例如大量计算。工作必须在 CPU 上完成，绕不开专门线程。

public async Task<int> CalculateResult(InputData data)
{
    var task = Task.Run(() => DoExpensiveCalculation(data)); // 排队到线程池
    // 此处可并行处理其它工作
    return await task;
}

注意：async/await 只是提供了与后台线程交互的干净写法，并不为共享数据提供任何锁保护，涉及共享状态仍需自己同步。

对调用者而言两者写法一致，区别只在资源性质：I/O 受限不占线程，CPU 受限要占线程。

6.5 .NET 历史上有哪三种异步模式？ ​

模式特征现状
TAP（基于任务的异步模式）单个 XxxAsync 方法返回 Task/Task<T>，.NET Framework 4 引入，async/await 提供语言级支持推荐，现代 .NET 唯一应该用的
EAP（基于事件的异步模式）XxxAsync 方法 + XxxCompleted 事件 + 事件参数类已不推荐新开发使用
APM（IAsyncResult 模式）BeginXxx / EndXxx 成对方法已不推荐新开发使用

以 Read 为例，TAP 只需 Task<int> ReadAsync(...)；而 EAP 要额外定义委托和事件参数类型，APM 要写 BeginRead/EndRead 两个方法。理解后两种主要是为了读老代码。

6.6 Task 有哪些状态？冷任务和热任务是什么？ ​

TaskStatus 枚举描述任务生命周期：

Created, WaitingForActivation, WaitingToRun, Running,
WaitingForChildrenToComplete, RanToCompletion, Canceled, Faulted
1
2

其中 Canceled、Faulted、RanToCompletion 是最终状态，处于最终状态时 IsCompleted == true。

  • 冷任务：用 new Task(...) 构造函数创建、状态为 Created，必须调用 Start() 才启动。
  • 热任务：Created 以外的状态，一定已经被激活过。

一个真实的坑：TAP 方法返回的任务必须已激活。如果内部用 Task 构造函数实例化并返回，调用方 await 一个从未 Start() 的冷任务会永远等下去。所以要么用 Task.Run/async 方法（自动激活），要么在返回前显式 Start()。

6.7 如何取消异步任务？进度如何上报？ ​

（1）取消：CancellationToken

可取消的异步方法会暴露一个接受 CancellationToken 的重载（约定参数名 cancellationToken）：

var source = new CancellationTokenSource();
var task = DoWorkAsync(source.Token);
source.Cancel();   // 请求取消

public async Task DoWorkAsync(CancellationToken token)
{
    while (!token.IsCancellationRequested)
    {
        await Task.Delay(1000, token);
    }
    token.ThrowIfCancellationRequested(); // 或返回 Task.FromCanceled(token)
}

（2）进度：IProgress<T>

var progress = new Progress<int>(n => Console.WriteLine($"当前进度：{n}%"));
await DoWorkAsync(progress);

public async Task DoWorkAsync(IProgress<int> progress)
{
    for (int i = 1; i <= 100; i++)
    {
        await Task.Delay(100);
        if (i % 10 == 0) progress?.Report(i);

}

6.8 Task.Yield 有什么用？ ​

Task.Yield() 返回一个"什么也没做"的空任务，await 它等于在异步方法里插入一个让步点：让出控制权、去线程池重新排队，让排在后面的任务先被分配线程。

await Task.Yield(); // 主动让一次，避免长时间霸占线程
1

适用场景是让一个长循环式的异步任务对其他任务更友好，属于调度层面的优化，语义上不改变结果。

6.9 ConfigureAwait(false) 解决什么问题？ ​

先看会死锁的经典写法：

private void button1_Click(object sender, EventArgs e)
{
    var content = CurlAsync().Result; // WinForms / 早期 ASP.NET 中会死锁
}
private async Task<string> CurlAsync()
{
    using var client = new HttpClient();
    return await client.GetStringAsync("http://example.com");
}

原因：UI 线程被 .Result 阻塞等待，而异步任务完成后要**回到原同步上下文（UI 线程）**继续执行，双方互等。这类死锁只发生在有同步上下文的 WinForms / 早期 WebForm，Console 和 ASP.NET Core 中不会出现。

两种解法：

  • 调用方：老老实实 await，不要用 .Result / .Wait() 同步阻塞（推荐）。
  • 库作者：在通用库内部用 ConfigureAwait(false)，声明"不需要回到原上下文"，提高库对新手误用 .Result 的容错性。
return await client.GetStringAsync(url).ConfigureAwait(false);
1

配套结论：.Result、Wait()、GetAwaiter().GetResult() 这类同步等待会阻塞调用线程，应全部换成异步等待；await Task.Delay() 期间并不占用线程资源。

6.10 ContinueWith 用在哪？ ​

ContinueWith 在任务完成后安排后续工作，可以链式串联多个阶段，并指定各自的 TaskScheduler：

var ui = TaskScheduler.FromCurrentSynchronizationContext();
Task.Run(() => DoBackgroundComputation())
    .ContinueWith(_ => UpdateUI(), ui)
    .ContinueWith(_ => DoAnotherBackgroundComputation());

现在多数场景用 await 顺序写更清晰；ContinueWith 主要用于需要精细控制调度器，或在已有 Task 上动态附加延续的场合。注意前置任务若为 Canceled，后续延续默认也会受影响。

我要做什么用什么
发起一个不阻塞线程的 I/O 调用await 对应的 XxxAsync()
把重计算挪到后台await Task.Run(...)
跑一个很长的独立任务Task.Factory.StartNew(..., TaskCreationOptions.LongRunning)
支持取消方法加 CancellationToken 参数
上报进度方法加 IProgress<T> 参数
