RAG、微调、续训与智能体选型（知识点笔记） ​

来源：ai-agents-from-zero 第 1-3 章《RAG、微调、续训与智能体选型》（GitHub 仓库），原文配图与完整讲解见原站。整理于 2026-11-26。

五大工程模块中，提示词工程（1-2）之外的后四项——RAG、微调、续训、智能体——表面都在"增强模型能力"，实际解决的问题并不一样。本文提炼本章的选型地图与最值得记的知识点。

一、先诊断，再选型：四问定位根因 ​

真实项目里 AI 应用回答不好时，最忌讳"还没判断根因就说'要不要微调''要不要上 Agent'"。先问四个问题：

诊断问题常见现象优先考虑
模型是不是没看到资料？不知道公司制度、产品手册、最新公告，回答无引用依据RAG
模型是不是行为不稳定？格式飘、话术不统一、分类标签不稳、JSON 经常错Prompt 优化，必要时微调
模型是不是不懂领域语言分布？拿到资料也读不懂，专业术语和行业逻辑经常错续训，通常再配合 RAG
任务是不是需要多步执行？需要查资料、调接口、校验、重试、写入系统工作流或 Agent

判断方案的三条主线：**知识够不够、行为稳不稳、流程会不会动。**缺知识先看 RAG；缺输出风格、格式、指令遵循先看微调；缺领域底层语言能力才考虑续训；缺多步决策与工具调用再看智能体。

二、选型总顺序：成本从低到高 ​

  1. 先 Prompt：只是需求表达不清，先把输入、输出、约束写清楚；
  2. 再 RAG：缺资料、依据、最新信息或私有知识，优先建知识库；
  3. 再微调：长期行为不稳，且已有高质量样本和评测标准；
  4. 慎用续训：仅当模型对领域语言和知识分布系统性陌生；
  5. 流程固定先工作流：步骤明确、需要稳定可审计；
  6. 流程开放再 Agent：步骤会变、需要动态选工具、按中间结果调整路线。

后面的方案不是"更高级"，只是成本、风险和维护压力更高。能用轻方案稳定解决的问题，就不要过早引入重方案。

三、RAG：先查资料，再回答问题 ​

  • 最短定义：RAG = 先查资料，再回答问题。流程：提问 → 去外部知识库检索 → 把"问题 + 检索结果"一起发给模型 → 生成答案。重点不是改模型参数，而是在运行时给模型补上下文。
  • 与提示词工程的区别：Prompt 依赖提前写好的提示词，RAG 依赖提问时实时检索到的外部资料。
  • 为什么常是第一选择：大模型答不好的三类真实成因——知识过时、知识私有、证据不足——本质都是"模型没看到材料"而非"不会说话"。RAG 优势：更新快（改知识库即可）、成本低、可追溯（保留来源/页码/文件名）、贴近业务系统。

两阶段工作流程：

阶段步骤
索引（离线）读文档 → 清洗切分 → 嵌入模型转向量 → 文本块 + 向量 + 元数据写入向量库
问答（在线）问题向量化 → 召回相关片段 → 组装进 Prompt → 模型生成最终回答

RAG 从来不只是"向量库 + 大模型"。文档质量、分块策略、召回方式、重排策略、Prompt 组织方式，都会影响最终效果。

四、RAG 的四个常见误区与排查链路 ​

误区纠正
有知识库就一定不会幻觉只能显著降低：检索错、噪声多、Prompt 没约束好仍会答错
文档全塞进去就行关键不是数量多，而是"能不能把相关的那几段稳稳找出来"
RAG = 向量检索真实项目常结合关键词检索、过滤、重排、元数据约束
RAG 能替代一切训练只解决"没看到知识"，不解决"不会按固定风格/格式输出"

效果不理想时沿链路排查（从轻到重）：文档质量 → 文档解析 → 文本切分（chunk size / overlap / 按标题层级）→ 召回策略（Embedding / Top-K / 元数据过滤）→ 重排序（Reranker）→ Prompt 增强（要求引用资料、缺依据时说"不确定"）→ 生成模型。

RAG 失败先修检索链路，再看生成模型；不要把所有问题都归因于"模型不够强"。

五、微调：改模型的"行为方式"，不是灌知识 ​

  • 定位：微调在已训练好的基础模型上用特定数据继续训练，让模型在某类任务/风格/输出形式上更稳定。它改的是"行为方式"，不是外挂知识库——不适合承载高频变化的知识，知识常变仍优先 RAG。
  • 何时需要：① 行为不稳定（JSON/SQL/分类标签飘、多轮提示仍漏字段漏步骤）；② 风格话术需长期固化（客服口吻、报告规范、品牌语气）；③ Prompt 已反复优化但仍不稳。
  • 何时可以微调（前提）：数据足够（高质量、任务相关、标注明确，否则是"把噪声训练进模型"）；评测标准清楚（先做评测集和验收标准，再谈训练）；算力与预算可接受。

技术方法：

方法思路
全参数微调更新全部参数，上限高但资源/显存开销大
LoRA冻结原模型大部分参数，只训新增的低秩适配参数
QLoRALoRA + 低比特量化，进一步降低显存
Adapter / Prefix / P-Tuning v2层间插适配器 / 可学习虚拟前缀 / 每层可训练提示向量

工程认知：今天大多数团队自己做微调，优先考虑的不是全参，而是 LoRA / QLoRA 这类 PEFT 路线。

主要风险：过拟合（训练集很好、真实场景拉胯）、灾难性遗忘（学新任务冲掉原有能力）、样本偏差（把团队偏见和噪声学进去）、评测幻觉（只看少量样例就下结论）。微调前后都要自问：我解决的是长期、稳定、可评测的行为问题，还是只是觉得 Prompt 不顺手？

六、RAG vs 微调：缺知识看 RAG，缺行为看微调 ​

维度RAG微调
核心目标给模型补充外部知识让模型更稳定地按目标做事
是否修改参数否是
擅长解决私有知识、最新知识、可追溯风格、格式、指令遵循、分类
更新速度快，改知识库即可慢，需重新训练
成本结构系统开发成本为主数据、训练、评测成本为主
典型场景文档问答、知识库、客服知识结构化输出、统一话术

七、续训：让模型"更懂某个世界" ​

  • 定义：Continued Pretraining——通用预训练完成后，用某领域大规模原始语料继续训练，补领域语言分布、术语体系和知识结构。用海量无标注文本，而非"指令-答案"样本。
  • 一句话区分：续训让模型"更懂某个世界"，微调让模型"更会按要求做事"。
  • 何时考虑：领域语言分布系统性缺失（不是差几个术语，而是整套表达"不像这个行业的人"），且 RAG 和微调都补不上。典型：法律/医疗/金融/代码语料领域适配、新语言适配。
  • 门槛：数据 GB~TB 级原始文本、算力远高于微调、业务收益要足够大——多数企业项目用不到，很多问题 RAG + Prompt 或 RAG + 微调 已能解决。
  • 误区：拿 SFT 问答对去续训（续训是语言建模）；把领域知识缺失全交给微调（模型连领域"说话方式"都不熟时微调不稳）；企业项目动不动就想续训。
维度微调续训
训练目标改行为方式改知识/语言分布
数据形式指令、对话、标签大规模原始文本
依赖标注强依赖通常不依赖
数据规模千~十万级十万级~海量
算力成本低到中高

组合拳顺序不能反：通用基座 → 领域续训（补分布）→ 指令微调（对齐行为）→ RLHF/RLAIF。若先微调再做大规模续训，前面学到的行为模式会被冲掉。大多数应用团队的路径是：选好基座 → Prompt + RAG + 工作流/Agent 做应用层增强，行为稳定性或领域分布确实成瓶颈才进训练。

八、智能体：大模型 + 工具 + 状态 + 执行流程 ​

**智能体 = 大模型 + 工具 + 状态 + 执行流程。**智能体不是"更强的大模型"，而是能理解目标、决定下一步、选择是否调工具、接收结果、继续决策直到完成任务的系统。

  • 五大核心要素：LLM、记忆（Memory）、工具调用（Tools）、规划决策（Planning）、行动执行（Action）。
  • 与单纯大模型的本质区别：大模型负责"生成回答"（会告诉你"可以查天气 API"），智能体负责"围绕目标持续决策并执行动作"（真的去调 API，再把结果组织成回答）。
  • 何时需要：任务多步骤、要调外部工具（搜索/数据库/浏览器/发消息）、中间结果影响后续动作、需要状态管理/规划/重试/反思。

粗略区分：Prompt 是"把问题问清楚"，RAG 是"先给模型补资料"，Agent 是"把一件事做完"。

九、Function Calling 与 MCP：模型决定，程序执行 ​

Function Calling 五步闭环：① 告诉模型有哪些工具 + 用户说了什么 → ② 模型返回"调哪个工具、传什么参数"（tool_calls）→ ③ 我们的代码真正执行工具 → ④ 把工具结果塞回对话再请求模型 → ⑤ 模型根据结果生成最终回答。

本质分工：**模型负责决定，程序负责执行。**模型并不会真的去调天气接口，它只输出"应该调用哪个工具、传什么参数"。

核心形态（以 DeepSeek 为例，节选）——工具声明：

  "parameters": { "type": "object",
    "properties": { "city": { "type": "string" } },
    "required": ["city"] } }}]

FC 的不足：工具实现与复用成本高（与业务环境耦合重）；规范碎片化（各厂商格式、字段命名不一致）；可靠性依赖工具描述质量（描述不清就调错工具、传错参数）。

MCP（Model Context Protocol）：把"工具、资源、提示模板"等能力按统一方式暴露出来的开放标准接口——像 AI 世界的 USB-C。注意：模型并不"认识 MCP"本身，它认识的是"这次请求里有哪些可用工具"。

Function CallingMCP
是什么模型调用工具的能力一套标准化通讯协议
关注点模型怎么表达"我要调哪个工具"工具/资源怎么统一暴露、发现、复用
作用让模型能调用外部能力让外部能力被不同 AI 应用统一接入
适用层模型调用层应用接入层 / 工具生态层

十、工作流 vs Agent：固定用工作流，动态交 Agent ​

  • 工作流（Workflow）：强调固定步骤和可控执行，把复杂任务拆成明确步骤按预设顺序执行（如：先分类 → 检索 → 生成 → 校验 → 输出）。
  • 判断标准：步骤固定、顺序明确、强调可控稳定 → 工作流；步骤不固定、需动态选工具和持续决策 → Agent。
  • 真实系统常是两者结合：固定部分用工作流，动态部分再交给 Agent。例：电商问数 = 工作流主导（召回 → 生成 → 校验 → 执行）+ 大模型在关键节点参与决策。

十一、最值得记的口诀 ​

  1. 三线判断：知识够不够（RAG）、行为稳不稳（微调）、流程会不会动（工作流/Agent）。
  2. 选型口诀：先 Prompt → 再 RAG → 再微调 → 慎用续训；流程固定先工作流，流程开放再 Agent。
  3. RAG 补知识：运行时补上下文，改知识库即生效、可溯源；失败先修检索链路再看模型。
  4. 微调改行为：前提是数据够 + 评测清楚；主流路线 LoRA/QLoRA；不承载高频变化的知识。
  5. 续训补分布：GB~TB 级原始语料，多数企业项目用不到；组合训练先续训补分布、再微调对齐行为，顺序不能反。
  6. 智能体做执行：不是更强的大模型，而是"大模型 + 工具 + 状态 + 执行流程"；Function Calling 是模型侧调用能力，MCP 是工具侧标准化暴露，模型永远只"决定"，"执行"在程序侧。
