提示词工程基础（知识点笔记） ​

来源：ai-agents-from-zero 第 1-2 章《提示词工程基础》（GitHub 仓库），原文配图与完整实操案例见原站。整理于 2026-11-26。

本篇是五大工程模块的第一层（成本最低、见效最快），本文提炼其中最值得记住的知识点：提示词是什么、六要素怎么写、Zero/Few-shot 怎么选、System/User/Assistant 怎么拆、以及 Prompt 什么时候不够用。

一、什么是提示词与提示词工程 ​

  • 提示词（Prompt）：发给模型的输入内容，可以是一句话，也可以是一整套结构化消息。工程视角下，Prompt 不只是"一句话问问题"，而是把角色、任务、上下文、输入和输出规则组织清楚。
  • 为什么需要提示词：模型读过海量语料，但不会主动知道"你这次想让它做什么"。提示词的作用是告诉模型：扮演什么角色、任务是什么、可以参考什么资料、输出成什么样子。

    提示词不是在"教模型重新学知识"，而是在激活它当前最该用的那部分能力。

  • 为什么需要优化：高质量 Prompt 不是把模型"变聪明"，而是减少歧义、减少跑偏、减少格式错误。类比看医生：只说"我不舒服"没法判断，说清症状、持续时间、触发条件判断才准。输入越模糊，输出越容易漂。
  • 提示词工程（Prompt Engineering）：系统地设计、组织、测试和优化 Prompt，让模型在特定任务、约束和上下文下尽可能稳定地产出符合目标的结果。它不是玄学，有效与否看五件事：需求表达是否清晰、输入边界是否明确、输出结构是否可验收、示例是否足够说明边界、约束是否自洽。

二、上下文与上下文窗口 ​

概念含义由此推出的工程结论
上下文（Context）这一次实际喂给模型的全部输入：System 提示词 + 用户问题 + 历史对话 + 检索结果 + 工具返回学 Prompt、RAG、工具调用，本质上都在学"如何组织上下文"
上下文窗口模型一次最多能处理多长的上限（由架构和训练决定），超出会被截断、压缩或放不进长文档不能无脑全塞；多轮对话要做摘要或裁剪；资料太多时往往要用 RAG

三、重心的变化：从"炫技巧"到"可检查的任务设计" ​

  • 早期模型能力弱，开发者依赖"技巧型 Prompt"：复杂提示链、花式引导语、大量显式推理提示。
  • 模型变强后，重点转向**"把需求说清楚，并让结果可检查"**。要问的不再是"要不要加某个神秘句式"，而是：任务定义清楚了吗？输入边界明确吗？输出格式可验收吗？背景和示例给够了吗？
  • 技巧（Few-shot、分隔符、结构化输出、逐步拆解）仍有价值，但作用是让任务更清楚、更稳定、更容易验证，而不是靠某句神秘话术让模型突然变强。
  • 工程系统需要的不是"偶尔答对一次"，而是能长期稳定复现，并可通过样例集或评测标准判断好坏。

    提示词不是咒语，关键是把需求写到模型能执行。

四、核心六要素：一段可执行提示词的构成 ​

要素回答的问题关键写法
角色你现在是谁不是贴花哨身份，而是控制口吻语气、专业深度、思考视角、任务边界
任务你要做什么指令动词开头（分析/总结/提取/分类/翻译/生成/重写/排序）+ 明确、具体、无歧义
背景/上下文还需要知道什么涉及特定读者、业务背景、历史记录、参考资料时很重要；不是堆资料，而是给更准确的理解起点
输入数据本次处理哪段内容用分隔符把指令、背景和原文隔开
输出格式结果长什么样JSON（程序处理）、Markdown（文档报告）、表格（分析对比）、代码；结果还要交给程序/工作流/解析器时必须先说清楚
质量与约束怎样算好、哪些事不能做质量标准（文风、语气、粒度、专业程度）+ 约束条件（字数、来源限制、禁止编造、合规边界）
  • 六要素不必每次写满，但它们是系统性检查 Prompt 是否完整的清单；任务越具体，模型越容易稳定命中目标。反例→正例："给我一个英语的学习计划" → "你扮演一名优秀的小学英语讲师，我是一名 3 年级学生，给我一个为期 3 个月提高英语成绩的学习计划"。

五、分隔符：把"指令"和"输入"分开 ​

  • 常见分隔符：三个反引号、三个双引号（"""）、<<< >>>、<>、<tag></tag>——用哪种不绝对，关键是一致且明确。
  • 原文经典案例：直接说"将下面的这句话翻译成英文。尽量使用华丽的词语"，模型把"尽量使用华丽的词语"当成了待翻译文本；改成"把用三个引号括起来的文本翻译成英文"并用引号包住原文后，输出才正确。

    如果不把"任务说明"和"原始输入"分开，模型就可能把输入文本本身当成新的任务去执行。

六、Zero-shot 与 Few-shot ​

方式做法适用场景特点
Zero-shot不给任何示例，直接让模型做任务任务常见、目标边界清楚、模型已具备相关能力简单、快、成本低；任务边界模糊时稳定性不如 Few-shot
Few-shot先给几个示例，再让它按示例完成新任务分类、抽取、改写、风格模仿、结构化输出——"光靠解释还不够，最好直接告诉模型什么算对"示例直接把目标风格演示给模型看
  • Few-shot 常见格式：多组 Q: <问题> / A: <答案>，最后留 Q: <新问题>? A: 让模型续写。
  • 原文经典案例：直接问"圣诞老人会给我带礼物吗"，模型回答"虚构角色"拆台；先给一组"牙仙是真的吗？答：当然！……"的示例演示"配合想象"的风格，模型就跟着示例风格走。

    示例不是"再解释一遍任务"，而是直接把目标风格演示给模型看。

  • 示例怎么选才不带偏：覆盖真实边界（常见输入、边界输入、容易误判的输入 + 对应正确输出）；示例格式要和最终期望完全一致，否则模型会学到错误模式。

七、结构化组织：System / User / Assistant ​

为什么要结构化（三个原因）：模型没有真正的持久记忆（想保留上下文，历史内容仍要重新送进去）；固定内容和变化内容应该分开（每次整段重写既浪费 token 也不利维护）；项目开发需要可复用（系统角色、全局规则、用户输入、历史对话、工具结果来自不同模块）。

结构化 Prompt = 把不变的规则和会变化的输入拆开组织。

消息类型职责放什么
System全局身份、规则、风格和长期约束角色、长期任务边界、稳定背景、输出格式、质量与约束（稳定规则）
User当前任务输入本轮用户问题、输入数据、临时补充资料、外部资料/工具结果（动态输入）
Assistant承接历史回复历史回答、需要被后续轮次继续参考的中间结果

六要素、模板、消息结构是同一件事的三个层次：

层次解决的问题
提示词六要素该告诉模型哪些信息（写什么）
提示词模板如何组织成可复用结构（哪些固定、哪些运行时替换）
消息结构运行时放到哪类消息里（怎么装配）

六要素回答"写什么"，模板回答"怎么复用"，消息结构回答"运行时怎么装配"。

  • 落到后续章节：RAG 中动态上下文填充检索到的知识库片段；Agent 中工具返回、历史动作、观察结果不断追加进消息上下文；LangChain 中落到 PromptTemplate、ChatPromptTemplate、MessagesPlaceholder 等对象。
  • 真实项目里的 Prompt 更像一套输入装配规则：哪些固定、哪些动态、哪些来自知识库、哪些来自工具，最后怎么一起送进模型。

八、提示词工程的边界：什么时候单靠 Prompt 不够 ​

问题本质不再是"怎么问"，而是模型缺知识、缺流程、缺行为稳定性时，需要其他模块配合：

场景问题本质解决办法
参考资料太多资料接近/超过上下文窗口，"资料太多，模型吃不下"资料筛选、摘要，或直接上 RAG
多步骤复杂流程一次生成里容易跳步、漏步、顺序混乱把大任务拆成多个小 Prompt，或用工作流组织
指令遵循能力不足对格式、结构和复杂指令的遵循有天花板关键要求前置；仍不稳则换模型、结构化输出方案，甚至微调
缺少领域知识Prompt 再清楚也不能凭空补足知识优先补上下文或知识库；再进一步才考虑微调/续训
  • 位置敏感性：研究表明许多模型对提示开头和结尾位置的信息更敏感，中间部分更容易"丢失关注"——不要把最重要的要求埋在中间。

九、常见误区与注意点 ​

  1. 不要把礼貌当成优化核心："请、谢谢"通常不会显著提升效果。礼貌不是主要优化杠杆，清晰才是——影响结果的是任务是否清楚、边界是否明确、输出是否可验收。
  2. 多个任务不要混在一起：一个 Prompt 同时塞"先总结、再分类、再评价、再输出复杂 JSON"等太多目标，模型容易顾此失彼，效果明显下降；复杂任务拆开或用工作流串起来。
  3. 允许 LLM 说"我不知道"：总要求"必须回答"，模型更容易编。高风险、信息不足或需要事实依据的场景，应明确允许模型承认不确定性（如"如果您对任何方面不确定……请说'我没有足够的信息来自信地评估这一点'"）——这类约束对降低幻觉非常有帮助。
  4. 指令自相矛盾：一边要求"简洁"一边要求"详细全面"，模型会陷入冲突（"写一段简洁的详细介绍"天然不自洽）；必须兼顾多个目标时明确优先级。
  5. 不要迷信"魔法词"：Let's think step by step、Take a deep breath and think this through 等句式只在某些模型/任务/时期可能有帮助，绝不是稳定、通用、可迁移的万能钥匙。更可靠的做法：任务拆清楚、给足示例、明确输出格式、约束不确定时允许拒答。

    不要迷信一句"咒语"，要重视完整的任务设计。

十、Prompt 调优的正确姿势：有证据地迭代 ​

  • 过度优化陷阱：在词句上来回抠，收益微小；没有固定测试样例时，甚至不知道改动是真的变好了，还是"刚好命中某一次输出"。
  • 更值得优先优化的通常是：结构是否清楚、任务是否明确、输入是否分隔、是否缺示例、输出格式是否合理——而不是纠结"写请帮我还是请你帮我"。
  • 样例集迭代法：对稍微重要的 Prompt 保留 5-10 个真实样例，每次改完用同一批样例重测，比较格式正确率、事实错误、遗漏字段和人工评分，让调优从"凭感觉改词"变成"有证据地迭代"。
  • 换模型要重新调优：不同模型的指令遵循习惯、输出倾向、工具调用风格、上下文利用能力都不一样，一个模型上表现不错的 Prompt，换模型后往往需要重新验证和调整。
  • Prompt 调优本质是实验性工作：有方法也有试错，但有效的试错是基于结构、目标和评测来迭代，而不是无意义地反复换词。

十一、一页速记 ​

关键词一句话
提示词发给模型的输入 = 角色、任务、上下文、输入、输出规则的组织
六要素角色、任务、背景/上下文、输入数据、输出格式、质量与约束（完整性检查清单，不必写满）
Zero / Few-shot不举例 vs 先示范；任务边界说不清就用 Few-shot，示例要覆盖边界且格式一致
结构化System 放稳定规则，User 放动态输入，Assistant 承接历史结果
边界资料多→RAG；流程复杂→拆步骤/工作流；指令遵循差→换模型/微调；缺知识→知识库/续训
误区别指望礼貌和魔法词；任务别混；允许说"不知道"；用样例集有证据地迭代
